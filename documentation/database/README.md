# Database

PostgreSQL 16 is the single system of record. Prisma 6 is the only data access
layer; no raw SQL outside a migration. One schema, one generated client, one
migration history (ADR-0009).

## Conventions

| Concern      | Rule                                                                                                                            |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------- |
| Primary keys | `String @id @default(uuid())`, generated by Prisma, never by application code                                                   |
| Money        | `BigInt`, integer minor units; never `Float`, never `Decimal` (ADR-0003)                                                        |
| Timestamps   | `DateTime @default(now())`; `createdAt` on every table, `updatedAt` where mutable                                               |
| Tenancy      | Owned records carry `businessId`; isolation is enforced in the service layer from the principal's `activeBusinessId`            |
| Soft deletes | Only where the business requires history (businesses, products, reviews). `deletedAt DateTime?`                                 |
| Enums        | PostgreSQL enums via Prisma `enum`; a state change is a new migration, not a string                                             |
| Deletion     | Referential actions are explicit (`Restrict` for financial history, `Cascade` for owned children, `SetNull` for optional links) |
| Indexes      | Every foreign key is indexed; composite indexes lead with the filter column                                                     |

## Model Groups

### Identity and access — 5 models

`User`, `UserRoleAssignment`, `UserSession`, `UserAddress`, `AdminProfile`.

One `User` may hold many roles through `UserRoleAssignment`; the session stores
which role is active. `UserSession` holds the refresh-token digest, the device
label, IP, and user agent, and is the unit of revocation. `AdminProfile`
carries `department`, which is the sole basis of administrative authority
(ADR-0006).

Phones are stored normalized to `+963…` E.164 and unique. Passwords store the
`scrypt$N$r$p$salt$hash` string (ADR-0004).

### Geography — 5 models

`Country`, `City`, `DamazonZone`, `ZonePhoto`, and the coordinate-precision enum.

A `DamazonZone` is a delivery polygon with a service level and an availability
window. Zones are the unit of delivery pricing and of delivery-company coverage.

### Businesses and subscriptions — 7 models

`Business`, `BusinessDocument`, `RestaurantProfile`, `BusinessSubscription`,
`Invoice`, plus `BusinessType` (`MERCHANT`, `RESTAURANT`, `DELIVERY_COMPANY`)
and `SubscriptionPlan`/`SubscriptionStatus`.

A business is approved through a document set and a subscription; an unapproved
or lapsed business cannot publish. `Invoice` and `Payment` together form the
financial history and are never hard-deleted.

### Catalog and menus — 9 models

`Category`, `Product`, `ProductImage`, `ProductVariant`, `InventoryMovement`,
`MenuCategory`, `MenuItem`, `Ingredient`, `MenuItemIngredient`.

Catalog products belong to a merchant or restaurant business. Restaurant menus
are separate from the retail catalog because their items are composed from
ingredients and priced per menu, not stocked as variants. `InventoryMovement` is
an append-only ledger; on-hand quantity is derived from its sum, which keeps
stock movements auditable.

### Carts — 2 models

`Cart`, `CartItem`. One active cart per user. Cart items reference a
`ProductVariant` or a `MenuItem` depending on cart type; pricing is snapshotted
onto the line so a later catalog change does not silently alter an in-progress
order.

### Orders — 4 models

`Order`, `OrderItem`, `OrderStatusHistory`, `OrderType` (`RETAIL`,
`RESTAURANT`, `GROCERY`, `PHARMACY`), and `OrderStatus`.

`OrderStatus` is the eleven-state lifecycle from the business requirements and is
the authoritative set (ADR-0007). `OrderStatusHistory` records every accepted
transition with the actor (`OrderActor`), the timestamp, and an optional note,
so the customer-facing timeline is a projection of the audit trail rather than a
separately maintained string.

Orders are never deleted. Cancellation is a transition, and refunds are
`Payment` records.

### Delivery — 5 models

`DeliveryCompany`, `Driver`, `DeliveryTask`, `DeliveryTaskStatus`, plus
`DriverStatus`, `VehicleType`, `DeliveryAssignmentMode`, and
`DeliveryServiceLevel`.

A `DeliveryTask` is a unit of work assignable to one driver. Assignment modes
cover company dispatch, individual driver acceptance, and platform dispatch. Task
status advances independently of order status so a delayed courier does not
stall the order timeline.

### Payments — 2 models

`Payment`, `PaymentLog`. `PaymentMethod` includes `SHAM_CASH` and
`CASH_ON_DELIVERY`. Amounts are minor units. `PaymentLog` is append-only and
records every state change plus gateway callbacks, which is what payment
verification and reconciliation read.

### Engagement — 6 models

`Review`, `Favorite`, `Coupon`, `CouponRedemption`, `Conversation`, `Message`,
`Notification`.

`Conversation` is polymorphic over its participants so one thread can span a
customer, a business, and support staff. `Review` targets a product, a
restaurant, or a driver through `ReviewTargetType`. Coupons support fixed and
percentage discounts, and redemption rows make usage limits enforceable.

### Platform operations — 6 models

`AdminProfile`, `AuditLog`, `SystemSetting`, `AnalyticsEvent`, `SupportTicket`,
and the `AuditAction` enum.

`AuditLog` is append-only and records the acting principal, the action, the
target, and a JSON diff. `SystemSetting` is a typed key/value store for runtime
configuration that non-engineers may change.

## Money Columns

Every amount column is `BigInt` and holds integer minor units. The currency is
carried alongside the amount by convention on the owning record (`currency
String @db.VarChar(3)`), not by a separate table, because a marketplace order
settles in a single currency. Multi-currency settlement is out of scope; the
registry in `@damazon/shared-types` marks which currencies are enabled.

## Migrations

```
apps/backend/prisma/migrations/
  20260101000000_initial_schema/
    migration.sql
  migration_lock.toml
```

Workflow:

```bash
npm run db:generate   # regenerate the client after a schema change
npm run db:migrate    # create and apply a development migration
npm run db:deploy     # apply committed migrations (production)
npm run db:status     # show applied/pending state
npm run db:seed             # development only: reference data and demo accounts
npm run db:seed:reference # load only countries, cities, and categories (no demo accounts)
npm run db:reset      # drop, re-migrate, re-seed (local only)
```

`prisma.config.ts` loads the repository-root `.env` and then an app-local `.env`,
so the CLI and the running API read the same configuration. Migrations are
committed SQL and are reviewed like code; `db push` is not used.

## Local Infrastructure

The backend requires PostgreSQL 16. Redis is not currently used by API request
processing. On Windows, install PostgreSQL 16 using its official installer,
start the `postgresql-x64-16` service, and configure the local connection in the
repository-root `.env`. Then run:

```powershell
npm run db:deploy
npm run db:seed:reference
```

The Docker Compose file under `deployment/docker/` is optional; Docker is not
required for local development.

## Seed Data

`apps/backend/prisma/seed.ts` is idempotent. `db:seed:reference` creates only
the production-safe reference data:

- Syria plus four cities (Damascus, Aleppo, Homs, Latakia);
- 13 catalog categories;

The development-only `db:seed` additionally creates:

- 7 system settings;
- one verified account per platform role, all with password
  `Damaz0n!Seed2026`;
- a merchant, a restaurant, and a delivery company, each with products, a
  restaurant menu, and driver fleet data;
- a delivery zone attached to the customer account.
